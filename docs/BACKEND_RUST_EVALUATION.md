# 后端完全 Rust 化评估

日期：2026-11-21　范围：`src/`（Node/Hono 后端）整体迁移到 Rust，不含前端
前置阅读：`docs/UI_SHELL_TAURI_EVALUATION.md`（外壳选型）、`docs/OPENCODEX_ROUTER_DESIGN.md` §8（当前 Rust 边界）

**结论先行**

1. **技术可行，且有两处结构性利好**：TLS 指纹层（`native/codex-tls`）本来就是 Rust；数据库面很小（2 张表、约 60 条语句）。
2. **但收支比现在不成立**。全量 Rust 是**全有或全无**：只有把 Node 彻底移出运行时才有收益，
   而在此之前 200+ 人日的投入对用户零可见回报（Node 仍然要在包里）。
3. **建议**：维持「Rust 数据面 + Node 控制面」的现状，把预算花在两件低成本的事上——
   P1 的「减漂移」投资（~15 人日）与分发形态瘦身（~2 人日）。
   全量 Rust 的立项条件写在 §7，任一命中再启动。

| `auth/` | 42 | 8,072 | 账号池、客户端 Key、额度窗口、轮换、SQLite 持久化 |
| `proxy/` | 33 | 6,843 | 上游适配器、WS 池、SSE、代理池、错误分类 |
| `translation/` | 15 | 4,413 | 三协议 ↔ Codex 双向转换 |
| `opencode/` | 21 | 2,980 | 本次新增（目录/协议矩阵/池/回退图/Rust 客户端） |
| 其它 12 个目录 | 66 | 10,952 | models 1.6k、logs 1.4k、types 1.4k、services 1.1k、ollama 0.85k、tls 0.7k… |

对照：测试 **377 文件 / 71,543 行**（源码:测试 ≈ 1:1.56）；前端 54 文件 / 11,729 行。

### 1.2 最重的 8 个文件（决定迁移难度）

`model-store.ts` 1,000（模型目录合并与别名链）、`ws-pool.ts` 844（WebSocket 池，含早错/早关处理）、
`account-persistence.ts` 794（SQLite + JSON 双写）、`account-registry.ts` 721（账号状态机）、
`ollama/bridge.ts` 686、`codex-to-openai.ts` 648、`proxy-handler.ts` 600、`codex-to-anthropic.ts` 571。

### 1.3 Node 专属依赖的落点（决定"必须重写多少"）

| 依赖 | 直接引用文件 | 迁移含义 |
|---|---:|---|
| `hono` | **64** | 全部路由与中间件；换成 axum 需重写 12.5k 行 |
| `undici` | 10 | HTTP/代理 transport；`reqwest` 可直接替代 |
| `js-yaml` | 6 | 配置加载；`serde_yaml` 替代，但需保持 yaml 结构兼容 |
| `ws` | 3 | WebSocket 服务端；`tokio-tungstenite` 替代 |
| `better-sqlite3` | **2** | 持久化面很小：`CREATE TABLE` 仅 2 处、DML 约 60 处 |

`better-sqlite3` 只有 2 个文件用到，这是**最被低估的利好**：数据库迁移的主要风险（schema 兼容、用户数据丢失）
SUP 范围有限，可用"影子读 + 双写校验"完成。

## 2. 五道技术坎

| # | 坎 | 现状证据 | 难度 | 风险 |
|---|---|---|---|---|
| 1 | **TLS 指纹一致性** | `native/codex-tls` 已是 Rust（rustls 固定 `=0.23.36`、reqwest + socks） | 低 | 全 Rust 后**反而更简单**：去掉 napi 边界，直接进程内使用 |
| 2 | **协议转换层** 4,413 行 | 15 个文件，双向上千条断言 | 中 | 机械但易错；行为差异直接表现为客户端解析失败 |
| 3 | **WebSocket 池** 1,865 行 | `ws-pool` 844 + `ws-transport` 554 + `responses-websocket` 366 + `codex-sse` 101 | 中高 | 早错/早关/序号连续性都有测试钉死；`tokio-tungstenite` 语义需逐条对齐 |
| 4 | **账号/额度语义** 8,072 行 | 轮换策略、额度窗口、额度组、级联封号、CF 挑战冷却 | **高** | 这是全项目最"行为密集"的部分，没有规格文档，测试就是规格 |
| 5 | **管理面 12,546 行** | 64 个 Hono 路由 + zod；dashboard 15 个页面依赖 | 中 | 纯体力；可用 axum + garde/serde 重写，但量大 |

第 5 项还藏着一个机会：**重写而不是照搬**可以把管理面砍掉 30–40%（现有不少接口是历史遗留的细粒度 CRUD）。

## 3. 三条路线

### A. 全量 Rust（一次性重写）

| 阶段 | 内容 | 估算人日 |
|---|---|---:|
| P1 | transport + TLS + SSE/WS 中继（`tls/`、`proxy/*-upstream`、`ws-*`、`codex-sse`） | 25–35 |
| P2 | 模型目录 + 协议矩阵 + 回退图 + zen-free 池（无 DB 的纯逻辑） | 35–45 |
| P3 | 账号/客户端 Key 池 + SQLite 持久化（`auth/` 8.1k + `services/` 1.1k） | 60–80 |
| P4 | 管理面 + dashboard API + 日志 + ollama 桥 + 自更新（15.8k） | 80–100 |
| — | 测试重写（71.5k 行按行为重写，非翻译） | +30–40% |
| **合计** | | **220–300** |

### B. 分阶段吸并（strangler，Node 保留为壳）

把数据面逐步搬进 Rust，Node 只做控制面与兼容层。**当前已在这个路线上**（`native/ocx-router`，3.0 MB）。

| 阶段 | 内容 | 人日 | 完成后能否去掉 Node |
|---|---|---:|---|
| ✔ 已完成 | 路由层（三协议入站、header、重试、错误归一） | 已投入 | 否 |
| B1 | catalog + `/models` + 回退图 + zen-free 池进 Rust | 25–35 | 否 |
| B2 | SSE/WS 中继进 Rust | 20–30 | 否 |
| B3 | 账号池 + SQLite 进 Rust | 60–80 | 否 |
| B4 | 管理面收尾 + 去 Node | 60–80 | **是** |
| **合计** | | **165–225** | 只在最后一步 |

### C. 维持现状 + 减漂移（推荐）

- 不新增 Rust 范围；
- 花 ~15 人日把「双实现一致性」用契约测试锁死（同一请求分别走 TS adapter 与 ocx-router，比对归一后的事件序列）；
- 分发形态按外壳评估走 portable/Node SEA（~2 人日）。

## 4. 收益（全量 Rust 完成后的可量化部分）

| 指标 | 现状（Node 后端 + 打包 Node） | 全量 Rust | 差值 |
|---|---|---|---|
| 后端产物 | Node SEA ≈ 85–110 MB（压缩 30–45 MB） | 单二进制 8–15 MB | **−70~95 MB** |
| 含 web 资产的总发行物 | 35–50 MB（压缩） | 12–20 MB（压缩） | −23~30 MB |
| 常驻内存（后端） | 60–120 MB | 15–30 MB | **−45~90 MB** |
| 冷启动 | 300–800 ms | 30–80 ms | −0.3~0.7 s |
| 平台构建 | `better-sqlite3` 需原生编译（本机实测：无 VS Build Tools 时 `npm ci` 直接失败）、napi 预编译矩阵、Node ≥22.13 下限 | 交叉编译即可 | 运维面显著收敛 |
| 双实现漂移 | TS adapter 与 Rust 路由必须并行维护（设计文档 §10 已列为长期风险） | 单实现 | 风险归零 |
| 与 Tauri 的协同 | Tauri 必须先有 Rust 后端才有体积意义 | 直接成立 | 解锁 |

**不可量化但真实**：单一语言、单一行号栈、崩溃面收敛（无 V8 OOM、无事件循环阻塞）。

## 5. 收支比（关键判断）

| 方案 | 人日 | 换来 | 折算 |
|---|---:|---|---|
| C：减漂移契约测试 | ~15 | 消除双实现行为分歧（当前唯一的结构性技术债） | 高 |
| C′：分发瘦身（Node SEA/portable） | ~2 | 下载体积 300 MB→90 MB（见外壳评估） | 极高 |
| A/B 全量 Rust | **220–300** | 后端磁盘 −70~95 MB、内存 −45~90 MB、启动 −0.5 s、单二进制发行 | **≈ 每 1 人日换 0.3 MB 磁盘 + 0.3 MB 内存** |

对比参照：缓存治理 0.5 人日就能换 100–300 MB 磁盘；`codex-tls` 这类原生编译问题用 CI 缓存 + 预编译发布 3 人日即可缓解。
也就是说，**全量 Rust 的收益密度比现有替代方案低两个数量级**。

**全有或全无**是决定性的一点：B 路线的 B1–B3 合计 105–145 人日，做完之后 Node 仍然必须随包，
用户看不到任何变化；只有 B4 落地那一刻收益才释放。这意味着它是**产品决策**，不是工程优化。

## 6. 现在不建议做的理由（逐条）

1. **功能仍在快速扩张**（本会话已新增 `src/opencode/` 3.0k 行）。重写期与开发期重叠，等于同时维护两套行为。
2. **行为规格只存在于测试里**（71.5k 行测试即规格）。Rust 重写必须从测试反推语义，任何遗漏都会变成用户可见回归。
3. **没有用户可感知的痛点驱动**：Node ABI 问题只影响开发机搭建（一次性的），不是运行时故障。
4. **许可约束不构成障碍，但收益也不来自许可**：自研代码可自由迁移，但迁移不改变任何许可边界。
5. **与 Tauri 的协同是唯一"战略级"理由**，而 Tauri 本身在无 Rust 后端时收益接近于零——这是鸡生蛋问题，
   需要一次性投入 250 人日才能同时兑现两者。

## 7. 立项条件（任一命中再启动）

1. 目标变成**单文件分发**：用户不应安装 Node / 不应看到 `node_modules`。
2. 决定上 **Tauri**（外壳评估里 Tauri 的全部体积收益都依赖 Rust 后端）。
3. WS/TLS 行为继续高频变动（今天每改一次要付两遍成本）。
4. 有 **≥250 人日**预算且能冻结功能路线图 4–6 周。
5. 用户规模大到 Node ABI / Windows 构建问题成为**持续**的安装失败来源。

若命中 1 或 2，优先走 **B 路线**（增量吸并），因为它允许在任何阶段停下而不浪费已完成的 Rust 资产；
若命中 3，先做 C（契约测试），再按 B1→B2→B3 推进。

---

## 8. 如果要做，建议的顺序与护栏

1. **先锁契约**：三协议入站 × 流式/非流式 × 错误类别的 golden 用例集（现在是散落在各处的单测），作为 Rust 实现的验收基线。
2. **影子运行**：Rust 实现接流量但不返回（旁路比对），差异率 < 0.1% 才切流。
3. **持久化双读**：SQLite 迁移期让 Rust 只读打开、与 Node 结果比对，写仍由 Node 承担；确认后再反转。
4. **管理面按需重写而非移植**：砍掉历史遗留的细粒度接口，目标 8k 内。
5. **每阶段都有"停在这里也不亏"的验收**：B1/B2 完成即可单独发布（更快的模型目录、更稳的 WS），不依赖终局。

## 9. 风险清单

- **行为回归**：额度窗口、级联封号、CF 冷却这类逻辑没有文档，只有测试；误译会静默改变用户的额度消耗。
- **测试重写成本被低估**：71.5k 行测试按行为重写，通常不低于源码重写的 60%。
- **双维护期**：B 路线 105–145 人日的中间态里，两套实现必须同时通过 CI。
- **Windows 交叉编译**：`better-sqlite3` 换成 `rusqlite`（bundled SQLite）后仍需处理 TLS 原生根证书与代理池。
- **上游漂移**：OpenCode 网关的模型/协议在变（本次侦察就发现 `minimax-m3` 跨上游换协议），重写期撞上上游变更会放大成本。
